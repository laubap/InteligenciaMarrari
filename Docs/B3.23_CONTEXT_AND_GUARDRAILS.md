## 1. Finalidade

Este documento é a fonte de contexto para qualquer pessoa ou agente de IA que audite o repositório.

A auditoria não pode tratar nomes de pasta como prova de papel arquitetural. Em especial:

- parte relevante do runtime está localizada em áreas chamadas `Benchmark`;
- componentes `Experimental`, `Shadow`, `Counterfactual`, `DualBaseline`, `RegimeShadow` etc. podem participar do fluxo funcional real;
- código Legacy ainda é necessário para compatibilidade;
- o sistema foi validado e corrigido incrementalmente em B3.21/B3.22;
- `Benchmark = descartável` é uma conclusão proibida sem rastreamento de dependências.

A B3.23 deve produzir uma radiografia confiável antes de qualquer limpeza estrutural.

## 2. Guardrails obrigatórios

### 2.1 Auditoria READ-ONLY

Durante B3.23:

- NÃO alterar código;
- NÃO mover ou renomear arquivos/namespaces;
- NÃO apagar arquivos;
- NÃO fazer cleanup ou refactor em massa;
- NÃO atualizar pacotes;
- NÃO mudar configurações;
- NÃO executar migrations destrutivas;
- NÃO sobrescrever artefatos de benchmark existentes;
- NÃO reescrever a arquitetura.

Mudanças somente depois, em B3.24.

### 2.2 Regra de evidência

Não declarar bug apenas porque:

- o nome parece estranho;
- a pasta parece incorreta;
- há comentário antigo;
- existe duplicação aparente;
- o componente se chama Legacy/Experimental/Shadow;
- um endpoint tem nome ruim.

Para cada finding, registrar:

1. arquivo;
2. classe/método;
3. caminho de execução;
4. evidência;
5. impacto;
6. nível de confiança;
7. cobertura de teste;
8. recomendação;
9. risco da alteração.

### 2.3 Benchmark não é automaticamente benchmark puro

Foi confirmado que runtime e componentes funcionais dependem de código em áreas como:

- `Benchmark.RegimeShadow`;
- Dual Baseline;
- decisões experimentais;
- incident layer;
- rollout funcional.

Todo arquivo em `Benchmark/` precisa ser classificado por referências, DI, factories, configuração e chamadas reais.

### 2.4 Compatibilidade Legacy

`DetectorResult.EhAnomalia` Legacy deve permanecer compatível até decisão explícita.

Invariantes:

- Feature OFF preserva Legacy;
- persistência das análises é intencionalmente ampla;
- RuntimeDecision é a decisão operacional posterior;
- interpretação/LLM deve seguir a decisão operacional final;
- rollout/canário não deve ser quebrado.

## 7. B3.22 — correções realizadas

### B3.22.3 MaxLag

- vetores defasados não desaparecem;

**Status: PASS**

### B3.22.4 Frozen Sensor

- sinais contínuos;
- deadband;
- mínimo de pontos/duração;
- variabilidade prévia;
- prioridade de Data Quality;
- evidência funcional sem depender de Legacy.

**Status: PASS**

### B3.22.5 Increasing Noise

Corrigidos:

- detector;
- arbitragem;
- cadeia experimental;
- decisão funcional;
- hysteresis;
- continuação;
- prevenção de chatter;
- supressão de LLM repetido em continuidade.

Resultado controlado: 1 início + 92 continuações, sem restart falso.

**Status: PASS**

### B3.22.6 Consistência P1

Descoberta central:

`AnomaliasDetectadas` funciona como histórico amplo de análises e contém registros normais e anômalos.

Correções:

- `DashboardGeralController.cs`: contar/listar somente `EhAnomalia == true` quando a métrica é de anomalias;
- `FeedbackAnomaliaController.cs`: feedback apenas para registros realmente anômalos;
- `NotificacoesController.cs`: `"Anomalia detectada"` para anomalia, `"Risco elevado"` para risco sem anomalia;
- `ConhecimentoIaController.cs`: métricas de anomalia filtradas por `EhAnomalia`; distribuição de risco não;
- `AnomaliaHistoricoController.cs`: histórico de anomalias filtrado por `EhAnomalia`;
- `PerfilTagController.cs`: lookup de processo corrigido para `ClienteId + TagName`, eliminando risco de tenant crossing.

Testes de consistência adicionados.

### LLM
- OpenAI aparentemente off/não usado no contexto atual;
- remanescentes de Ollama;

- configuração/modelo pode divergir;
- auditar logging bruto.

Possivelmente privado/não usado. Confirmar referências.

### CandidateFactory.Trace
Possível no-op. Confirmar.

### Monitoramento
- compartilhamento de `PredictionService`;
- execução sequencial;
- espera ~1 minuto;
- logs intercalados.

### Sanitização repetida
Mapear duplicações de preparação/sanitização de histórico.

### Invalid input
Risco de entrada inválida aparecer como resposta normal com detectores vazios em alguns fluxos.

### Experimental summary
`semantics.experimentalNewAnomaly` pode ter semântica textual desatualizada após Frozen/Increasing Noise.

### RegimeShadowOptions
Comentário pode dizer "experimental" enquanto defaults participam de runtime.

### Persistence evidence adapter
Auditar se duração > 0 pode virar evidência mesmo sem voto real do detector.

### Regime trace esparso
Ausência de minuto no trace não significa ausência de avaliação.

### `regimeEpisodeId`
Auditar semântica em continuations.

### Dual baseline trace vazio
Pode ser esperado quando DecisionCounterfactualEnabled está ativo.

### Results
Reuso de pasta pode misturar execuções. Nova prática usa diretório único.
